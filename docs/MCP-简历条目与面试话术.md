# MCP 项目沉淀 · 简历条目与面试话术

> 项目：wholesale-agent（批发业务 AI 助手 + 自研 MCP Server）
> 用途：求职材料与面试准备。所有表述均与代码实况一致，边界说明见文末第四节。

## 一、项目一句话（三个长度，按场合选）

**超短版（10 秒，自我介绍时用）**

> 我自研了一个 MCP 工具服务，让 AI Agent 能直连企业 ERP 读真实数据。

**标准版（30 秒，简历摘要 / 面试开场）**

> 基于 MCP 协议自研工具服务端，封装了 RAG 知识检索与企业 ERP 数据接口两类能力，让 AI Agent 能带鉴权读取真实业务数据。

**详细版（80 秒，被追问时展开）**

> 项目是我自己做的批发业务 AI 助手，前端 Next.js，后端 TypeScript。核心有两层：第一层是 RAG 检索链路，从文档切分、向量化、混合检索到重排序和召回评测都是自己实现的；第二层是用 MCP 协议写的一个工具服务端，把「知识库检索」和「ERP 接口调用」封装成 AI 可调用的标准工具。最有价值的部分是打通了企业 ERP 的鉴权——那是公司的 ThinkPHP 系统，我不能改它一行代码，全部通过外部请求头适配实现，现在能拉到真实的库存、客户、采购数据。

## 二、简历条目（两个版本，按投递岗位选）

### 版本 A · 投前端 / 全栈岗

**批发业务 AI 助手（个人项目）**　2026.08 – 至今

- 基于 Next.js + TypeScript + Vercel AI SDK 独立开发批发业务 AI 助手，覆盖前端交互、服务端接口、检索增强全链路
- 自建 RAG 检索链路：文档切分 → bge-m3 向量化（1024 维）→ 混合检索（向量 + 关键词 + RRF 融合）→ 重排序 → 元数据过滤 → 同文档去重，配套 Recall@k 评测脚本量化召回质量
- 基于 MCP 协议（Model Context Protocol）自研工具服务端，采用 **stdio 与 Streamable HTTP 双传输**（同一套工具注册代码同时支持本机与远程接入），配合 Zod 参数校验与 Bearer token 服务端集中鉴权
- 逆向分析 ThinkPHP/Niushop 系统的会话与响应机制，通过登录态注入 + 请求头适配从外部打通后台数据接口，实现 AI 读取真实库存、客户、采购数据，**未改动业务系统任何代码**
- 项目部署至 EdgeOne Pages，积累 SSR 与 API 路由的生产环境适配经验

`技能标签`：TypeScript · Next.js · Node.js · MCP · RAG · RESTful API · ThinkPHP

### 版本 B · 投 AI 应用 / Agent 岗

**企业级 AI Agent 工具层开发（个人项目）**

- 基于 MCP 协议自研工具服务端（Node.js + TypeScript + @modelcontextprotocol/sdk），定义工具 schema 与参数校验，通过 stdio 传输接入 WorkBuddy / Claude Desktop 等 Host 并完成真实调用验证
- 实现 stdio 与 Streamable HTTP 双传输架构：工具注册抽象为工厂函数（一连接一 Server 实例，为按调用者身份裁剪工具集预留扩展点），HTTP 入口采用有状态会话管理并实现 token 集中鉴权（实测无 token / 错误 token 均返回 401）
- 实践「检索型 + 接口型」两类工具范式：前者复用自建 RAG 链路返回文档片段与来源，后者通过登录态注入调用企业内部 ERP 的 HTTP 接口
- 打通「Agent → MCP Server → 企业 ERP（ThinkPHP）」完整链路，实测可读取库存总览（金额 4,108 万）、客户档案（420 条）、采购单（1,206 张）、交易记录（4,948 条）等真实业务数据
- 独立完成 RAG 检索链路的工程化与评测，使用硅基流动 bge-m3 生成向量，通过 RRF 融合与重排序提升召回质量
- 沉淀工具描述设计经验：工具名语义化 + 触发场景枚举提升 LLM 自动选中率；为鉴权失效等失败路径设计「可执行提示」，避免 LLM 基于错误内容编造回答

`技能标签`：MCP · Tool Use · RAG · TypeScript · Node.js · Prompt Engineering

## 三、面试话术

### 3.1 电梯版（30 秒）

> 我搭了一个批发业务的 AI 助手，它能查企业内部 ERP 的真实数据。核心是我用 MCP 协议写了一个工具服务端，把两类能力暴露给 AI：一类是制度知识库检索，一类是 ERP 接口调用。
> 最大的难点在鉴权——ERP 是公司的 ThinkPHP 系统，我不能改它，所以通过分析它的登录态机制和响应约定，用请求头适配的方式从外部打通了。现在能拉到真实的库存金额和客户档案。

### 3.2 技术版（2 分钟，分四段递进）

**第一段 · 为什么做（15 秒）**

> 起因是我在学 Agent 开发，学完 RAG 之后想验证一件事：AI 能不能真的操作企业内部系统。因为 RAG 解决的是「模型不懂你的私有知识」，但企业里更值钱的是「模型够不到你的系统」——库存、订单、客户这些实时数据，模型再强也变不出来。

**第二段 · RAG 层（30 秒）**

> 检索这块我做的是七步链路：文档切分、bge-m3 向量化、混合检索、重排序、元数据过滤、同文档去重、最后是召回评测。
> 混合检索是向量和关键词两路并行。单纯向量容易被近义词带偏，单纯关键词又不懂同义表达，所以用 RRF 做融合——它用排名倒数，不用归一化不同量纲的分数，也不用调权重，比加权求和稳。
> 评测这块我写了 Recall@k 脚本，准备「问题 → 期望文档」的标注集，改一次策略就跑一次，看指标涨还是跌。没有这个的话调参全靠感觉。

**第三段 · MCP 层（45 秒）**

> 工具层用的是 MCP 协议。为什么不用普通函数？因为函数是给「我自己的代码」调的，MCP 是给「任何 Host」调的。
> 区别在三点：一是自描述，工具名、描述、参数 schema 都由 Server 提供，Host 启动时自动发现，我不用给每个 Host 写适配；二是标准化传输，stdio 和 HTTP 都是协议规定好的；三是生态复用，同一个 Server 能同时接 WorkBuddy、Claude Desktop、Cursor，零改动。
> 我封装了两个工具，刚好是两种典型形态：一个是检索型，复用 RAG 链路返回文档片段；一个是接口型，去调 ERP 的 HTTP 接口。第二种才是 MCP 真正的用武之地——它是「动作」，模型自己永远做不到。

**第四段 · 最大难点（30 秒）**

> 最难的是打通 ERP 鉴权，过程基本是「猜测 → 实测 → 推翻 → 再猜」。
> 我一开始看源码看到 `if (!empty($params['token']))`，以为不传 token 就放行。实测 `/api/order/lists` 直接返回「token 不存在」——说明这个判断只覆盖部分接口。
> 后来定位到 `/erp/*` 和 `/crm/*` 是另一套体系，全部继承同一个基类，走后台登录态。挖到 session 名是 PHPSESSID，实测：不带 Cookie 跳登录页，带上就 200。
> 但拿到 200 之后还是报 500。这个坑最典型——控制器里有 `if (request()->isAjax()) return $list;` 直接返回数组，但配置里没设 `default_return_type`，框架不知道序列化成什么。解决办法是补两个请求头：`X-Requested-With` 让它进 ajax 分支，`Accept: application/json` 让框架选 JSON 响应。
> 最后固化成「请求头三件套」，缺一不可。这部分是我觉得最有含金量的——它是逆向 + 实测出来的，不是文档里能查到的。

### 3.3 高频追问 × 10（附标准答）

**Q1 · 为什么用 MCP，不直接写函数调用？**

> 函数是给「我的代码」调的，MCP 是给「任何 Host」调的。差在自描述、标准化传输、生态复用这三点——我不用为每个 Host 写一套适配代码。
> 但有一点要说清楚：MCP 本身不解决「LLM 会不会调」这个问题。那是 Host 侧的决策，Server 只能通过工具描述去影响，不能强制。

**Q2 · 你的向量库用的什么？**

> 是自建的内存向量库——一个数组存 chunk 和向量，手写余弦相似度。没用 Chroma 或 Pinecone。
> 原因是文档量小，只有几篇、几十个 chunk，引入向量数据库纯属负担。我预留了升级路径，代码注释里标了「生产环境可升级为 Chroma」。

**Q3 · 为什么用 bge-m3，不用 OpenAI 的 embedding？**

> 两个实际原因。一是网络，OpenAI 的 API 国内访问不了；二是成本，bge-m3 在硅基流动上免费且国内直连，1024 维，中文效果够用。这是工程取舍不是技术偏好。

**Q4 · 混合检索为什么要用 RRF？**

> 向量检索擅长语义但会被近义词带偏，关键词检索精确但不懂同义表达。要融合的话，加权求和需要调权重，而且两个分数量纲不同要先归一化。
> RRF 用排名倒数融合，天然免归一化、免调参，实践中更稳。这是我读完两种方案后的选择理由。

**Q5 · 你怎么判断检索质量好不好？**

> 写了 Recall@k 评测脚本，准备一组「问题 → 期望命中的文档」标注，跑一遍算 top-k 命中比例。
> 关键是让调参从「感觉」变成「数字」——每次改检索策略跑一次，指标涨就留、跌就回滚。

**Q6 · 打通 ERP 鉴权最难的地方在哪？**（同 3.2 第四段，可展开）

> 难在「猜测」到「验证」的循环。有个细节值得说：我一度以为 `/api/` 和 `/erp/`、`/crm/` 是三套鉴权，后来查基类才发现后两个全继承 BaseShop 且 `app_module` 都是 `shop`——所以一次店铺端登录就全线通行。这种结论只能靠读代码加实测拿到。

**Q7 · 为什么走 HTTP 接口，不直连数据库？**

> 直连库数据最全，但要自己处理 schema、字段含义、权限边界。走 HTTP 接口复用了系统本身的业务逻辑和权限校验——它认为什么数据该给、怎么算，我都不用重新实现。
> 而且我不改对方一行代码，风险最低。MySQL 就在本机，技术上直连也做得到，但接口方式更贴近真实企业集成的形态。

**Q8 · 这个工具有什么安全问题？**

> 有个明确的边界——它现在能读到全量客户资料（含手机号）和经营数据（库存金额）。所以只在本地调试用。
> 处理上：Cookie 写在 .env 里、已加 gitignore、不硬编码；生产环境需要工具级权限控制，只暴露必要字段。这个边界我自己是清楚的。

**Q9 · 听说 Agent 有时不自动调你的工具？**

> 对，实际存在。我试过改工具名（`query_knowledge` → `search_wholesale_policy`，更具体）、加强描述（明确写「必须优先调用、禁止凭记忆回答」并枚举触发场景），有改善但不稳定。
> 根因是调不调由 Host 侧 LLM 决定，Server 只能影响不能强制。而且实测发现 Host 有默认的澄清策略——遇到歧义问题会先反问而不是先调工具。
> 我的结论：显式指令 100% 生效，当正常用法；同时认清了这是 Host 特性不是 Server 缺陷——真实企业里不同 Host（Claude Desktop、Cursor）策略也各不相同。

**Q10 · 如果重做一次，你会改什么？**

> 三点。一是先定好 .env 加载顺序——我踩了坑，Server 里静态 import 模块会在 .env 加载前初始化客户端导致 key 读不到，正确做法是先加载 .env 再动态 import。二是工具描述一开始就该枚举触发场景，而不是写泛泛的「查询知识库」。三是最早该用命令行客户端验证而不是先装 Inspector——命令行能拿原始输出，排查快得多。

**Q11 · 你的 MCP Server 现在只能本地跑吗？**

> 两种形态都实现了，也都实测过。
> stdio 是本机开发形态——Host 拉起子进程，工具跑在我电脑上，凭证放本地 `.env`。HTTP 形态是企业部署的样子——Server 作为常驻服务，客户端通过 URL 接入，有状态会话管理，身份从 Bearer token 解析；实测无 token 和错误 token 都返回 401。
> 我的理解是：这两种形态的差别不在「本地还是远程」，而在**凭证和权限放在谁手上**。stdio 是「一个人拿全权账号给自己用」；企业要的是「一个共享服务，按人分配权限，全程留痕」。所以我把工具注册抽成了 `buildServer(caller)` 工厂——一连接一实例，扩展点留好了，后续按角色裁剪工具集只要在这个函数里加判断。
> 另外有个安全细节值得一提：工具参数里**绝不能出现调用者身份字段**。身份必须从凭证解析。否则用户一句「帮我查张三的客户」就能越权。

**Q12 · 为什么不用 Express 之类的框架？**

> 一开始打算用，但环境里缺类型包、npm registry 指向的域名已废弃，装不上。评估后改用 Node 原生 `http` 模块——MCP 只需要 4 个路由（POST / GET / DELETE / health），原生实现不到 60 行，还顺便看清了 body 解析和响应头的细节。
> 这个选择本身也说明一点：**能不加依赖就别加**。

| 免鉴权接口 | 早期判断「不传 token 就放行」是错的，已修正 | ❌ 沿用错误结论 |

## 五、可直接背的三句总结

1. **RAG 解决的是「模型不懂你的知识」，MCP 解决的是「模型够不到你的系统」。**
2. **能用规则算的，绝不交给 LLM 猜**——确定性逻辑写成工具代码，别塞进知识库让模型读。
3. **MCP Server 只能影响 LLM 调不调，不能强制**；这是 Host 侧策略，别把它当 Server 的 bug 修。
