## 一、电梯陈述（30 秒，背下来）

> 我做的是一个面向中小批发商的业务 Agent，叫批发通。它身上挂了三层能力：
> 一是**知识库检索**（RAG），回答退货、账期、客户等级这类制度问题；
> 二是**工具调用**，接客户欠款、库存、订单三类只读查询；
> 三是**工作流编排**，把催收这件事拆成状态图——查欠款、判风险、起草话术、人工确认。
> 技术栈是 Next.js + Vercel AI SDK + DeepSeek，另外单独起了一个 **MCP Server**，把知识库作为工具暴露给外部调用。

三个必须出现的点：**给谁做的** / **三层能力（都要带名词）** / **一个差异化（MCP）**。

## 三、9 个主讲述点

### 讲述点 1 · 项目定位与架构

**主张**：这是把 RAG、工具调用、工作流三种能力合成一个入口的 Agent，不是 demo。

**证据**
- `app/api/chat/route.ts` 文件头自己写着"三层能力已合体"
- `app/ChatPage.tsx` 有一条**能力标签条**，三种能力做成可视化 chip（面试演示时可以直接点）
- 示例问题按通道分组（`tool` / `kb` / `mix`），可以现场演示"哪条走哪路"

**要说的名词**：RAG、Tool Calling、Workflow Orchestration、混合通道

**追问怎么接**
- *"工具和知识库怎么协作？"* → 示例里有一条「李四是什么等级客户？有什么待遇？」：工具拿等级**数据**，RAG 拿等级**制度**，最后合并回答。**数据来自工具，规则来自文档。**
- *"为什么不做成两个入口？"* → 用户不会区分"这是查数据还是查制度"。**入口统一，路由交给模型。**

**别说错**：不要把它说成"聊天机器人"。它是"带工具和流程约束的业务入口"。

---

### 讲述点 2 · RAG：一条完整的检索链

**主张**：检索不是"向量查一下"，是**混合召回 → RRF 融合 → 交叉编码器精排 → 去重**四级管线。

**证据**（`lib/knowledge.ts` 的 `retrieve()`，第 352~401 行）
1. `applyFilter()`（323）**元数据预筛**：先按 category / tags 缩小候选池
2. 路一：**向量召回** top-20（余弦相似度）
3. 路二：**关键词召回** top-20（`lexicalScore`，中文近似 BM25，AND 语义）
4. `rrfFuse()`（242）**RRF 融合**，k=60
5. `rerankChunks()`（268）**交叉编码器重排**，bge-reranker-v2-m3，只跑 top-20
6. `dedupeBySource()`（338）**同文档去重**，防长文档多片挤占 top-K
7. `buildContext()`（407）拼成带 `[1] 来源：xxx.md` 的上下文，追加进 system prompt

**要说的名词**：混合检索 Hybrid Retrieval、RRF 倒数排名融合、交叉编码器 Rerank、元数据预筛 Metadata Filtering、双塔 vs 交叉编码器

**必须讲的一个取舍（这条最能证明你懂）**
> "RRF 用的是**排名**不是**原始分数**——向量分是 0~1 的余弦，关键词分是 0~1 的命中率，尺度不同，直接相加会被数值大的那一路主导。换成排名，两路都变成'第几名'，天然公平。"

**追问怎么接**
- *"为什么召回 top-20 而不是全库精排？"* → 交叉编码器要"query + 文档"拼起来过一次模型，**成本是 O(n)**，全库跑不动。只精排 top-20，是精度和成本的折中。
- *"chunk 重叠率怎么定的？"* →（这是你的缺口，见第六节答法）

### 讲述点 3 · 三级降级：知识库永不整挂

**主张**：外部依赖全部有兜底，**任何一环挂了都退到可用状态**，不整个请求 500。

**证据**
- `rerankChunks()` 有三处"优雅退出"：没配 key（273）／接口非 2xx（291）／抛异常（304）——全部 `return candidates` 回退融合结果
- 工作流同理：`classify` 挂了 → `classifyByRule`（规则）；`draftMessage` 挂了 → `draftByTemplate`（模板）
- `app/api/me/route.ts`：`cookies()` 单独 try 兜住，"任何异常都返回未登录，让前端有状态可渲染，不能卡住"

**要说的名词**：优雅降级 Graceful Degradation、兜底策略、可用性优先

**追问怎么接**
- *"降级了用户怎么知道？"* → 服务端打 `console.warn` 标记降级原因；**不给用户看**——用户要的是答案，不是内部分支。
- *"为什么不重试？"* → 检索场景超时重试只会更慢，**降级比重试划算**。重试适合写操作，兜底适合读操作。

### 讲述点 4 · 一次真实的策略迭代（v1 → v2）

**主张**：关键词召回踩过一次坑，我定位了原因并改掉——**这是有记录的调优，不是一次性写完**。

**证据**（`knowledge.ts` 第 214~218 行注释原文）
> v1 用字符命中率 → 单字"张"在不相关文档也会被命中并拉高分 → v2 改成 **AND 语义**（query 的每个实义字都必须出现才算命中），专名（张三 / 单号 A123）检索更准、不稀释

配套：停用词表过滤"的 / 了 / 吗"，避免这些字没出现导致整句误判。

**要说的名词**：分词策略优化、中文 BM25、误召回调优

**追问怎么接**
- *"改完有效果吗？"* → 诚实答：**方向是确定的（单字误命中被消除），但还没有量化**——这是我接下来要补的。（见第六节）
- *"还有什么可优化？"* → 注释里已经留了方案 b：**改成 2-gram**（"张三"拆成相邻组合）会更稳，只是当前数据量下 AND 已经够用。

**这个讲述点的价值**：它证明你会**发现缺陷 → 归因 → 给方案 → 留后续**，而不是"跑通就算完"。

### 讲述点 5 · 手写工作流引擎（45 行）

**主张**：我用 **45 行**实现了 LangGraph 的核心机制——状态图、条件边、状态补丁。

**证据**（`lib/collection-workflow.ts`）
- `nodes` 是 Map（名字 → 函数）、`edges` 是 Map（名字 → 下一个名字）
- 引擎就是一个 `while (current !== END)`（288~306 行）
- 节点返回 **Partial 补丁**，引擎用 `Object.assign(state, patch)` 合并
- **边可以是函数**：`edges.set('classify', s => s.risk === 'high' ? 'draftMessage' : END)`（268）——这就是条件边

**要说的名词**：StateGraph、条件边 Conditional Edge、状态归约 Reducer、Pregel 循环

**最强的证据是"引擎没改过"**
> "这个 `runGraph` 从第 3 步的 for 循环改成 while 之后**一个字都没改**。后面我加了 AI 分类、AI 写话术、换了数据源、加了两跳查询——`nodes` 和 `edges` 那两张表换了内容，引擎本身没动过。这就是**图与实现解耦**。"

**追问怎么接**
- *"为什么不直接用 LangGraph？"* → **先手写再上框架**：不手写一遍，用框架时它是黑盒；手写完再用，能看懂它的取舍。迁移成本对我很低。
- *"状态大了怎么办？"* → 现在 state 就 8 个字段，所以直接放内存；**上生产要换成 checkpointer 持久化**（见必问 Q7）。

### 讲述点 6 · 人审卡点（HITL）：为什么"不等人"

**主张**：人审不是"阻塞等待"，而是**在图里贴标签、把等待搬到图外**。

**证据**（`humanApprove`，237~239 行）
```ts
async function humanApprove(state: any) {
  return { needsApproval: true };   // 只贴标签，不等人
}
```
边：`edges.set('humanApprove', END)`——走到这里就结束这一轮。

**代码注释里写清了理由**（229~231 行原文）
> 网站上的 HTTP 请求不可能挂着等一个人——用户可能想 3 秒，也可能想 3 天。等待这件事没消失，它搬到了图外面：由调用方拿着草稿去问用户。

**要说的名词**：Human-in-the-loop、**deterministic guardrail（确定性护栏）**、中断 Interrupt、副作用隔离

**追问怎么接**
- *"用户第二天回来说'发吧'怎么办？"* → 现在接不上，因为图的状态不持久化。**这是我知道的下一步**：引入 `threadId` + checkpointer，把 state 落库，人审就能跨时间。
- *"为什么不让 AI 自己判断要不要发？"* → **发送是不可逆动作**。关键流程的结果不能交给模型解释，要能**保证**——这是护栏，不是提示词。

**这个点是差异化最大的一个**：绝大多数候选人做的是"AI 生成完直接输出"，你做的是"生成完必须停在人面前"。

### 讲述点 7 · 异常分层：catch 的位置决定语义

**主张**：`throw` 不是"程序出错"，是"**这张图不成立**"的信号；异常必须穿出整张图，在最外层拦成结构化结果。

**证据**
- `loadDebt` **故意没有 try/catch**（58~61 行注释原文）：查不到客户、没有订单、一笔未结清都没有——这三种都意味"图根本不成立"
- 三种情况都 `throw`（68 / 76 / 84），异常穿到 `tool.execute` 的 `catch`
- 最外层（344~346）：`catch (err) { return { found: false, message: err.message } }`

**反面案例（这段面试官最爱听）**
> "我一开始把 catch 放进了 `loadDebt`。结果客户不存在时，异常被降级成数据混进了上下文——AI 拿着**不存在的客户**写了一封真情实感的催款信。
> 那一刻我明白了：**在节点里 catch 等于把异常变成幻觉的原料**。catch 的位置决定了语义——放在节点里是"降级成数据"，放在最外层是"把原因交出去"。"

**要说的名词**：故障传播语义、异常分层、幻觉源头治理、fail-fast

**追问怎么接**
- *"那 AI 判风险失败为什么又允许降级？"* → 两种失败性质不同：**数据缺失是"图不成立"（必须终止）**，**AI 调用失败是"这一环降级"（可以兜底继续）**。因为前者产出的结果没有意义，后者用规则替代仍然有效。

### 讲述点 8 · 上下文工程：工具返回值必须自解释

**主张**：给 AI 的返回值**不能靠"少了哪个字段"表达状态**，必须有显式字段说明发生了什么。

**证据**（`collectionWorkflow.execute`，337~343 行）
```ts
let data = { customer, amount, days, risk, reason, message, draftedBy, needsApproval };
if (!message) {
  data.outcome = 'skipped';
  data.note = '该客户风险等级为常规，按规则本期不催收，未生成草稿。请如实告知用户本期不催收，不要自行编写草稿。';
}
```
- 低风险：`outcome: 'skipped'` + `note` 指令
- 查不到：`{ found: false, message }`
- 成功：8 个业务字段

**还有一个动作叫"瘦身"**：图内部 state 有很多中间字段，工具只挑 8 个交给 AI——**返回值会进上下文，给多了就是污染**（`lib/tool.ts` 第 9~10 行同样写着这条）。

**要说的名词**：上下文工程 Context Engineering、工具契约设计、返回值自解释、上下文污染

**追问怎么接**
- *"为什么不让 AI 自己推断？"* → 模型对"缺失"的默认反应是**补全**，不是追问。所以必须显式告诉它"什么都没发生，原因是 X"。
- *"note 里为什么要写'不要自行编写草稿'？"* → 因为模型的默认倾向是"用户要催款，我该给个草稿"。**边界必须写出来，不写就等于不存在。**

### 讲述点 9 · 工程底座（最容易被忽略、但最能证明"能上生产"）

**主张**：业务代码之外，我把外部依赖收成了三层可控边界——**统一出口、统一凭证、统一错误**。

**证据**
- `lib/api.ts`：所有外部请求走一个 `request()`；`AbortController` 10 秒超时 + `finally` 清定时器；错误四分类（业务 4xx / 超时 / 网络 / 其他）**全部转成中文**给 LLM 读
  > 注释原文：「改域名 / 加鉴权 / 加超时 / 统一错误处理——只改这一个文件」
- `app/api/login/route.ts`：密码换 `httpOnly` cookie（`sameSite: 'lax'` + `maxAge` 7 天）
- `app/api/me/route.ts`：**双凭证解析**——浏览器读 cookie，小程序读 `x-site-token` 头
  > 注释原文：「小程序对 Set-Cookie 的自动管理在真机上不可靠，改由前端手动携带」
- `app/api/mock/[resource]/route.ts`：**表驱动**设计，加一个数据类型只加一行 `HANDLERS`，不用新建文件

**要说的名词**：统一数据通道、错误归一化、超时控制、多端凭证适配、表驱动、12-Factor 配置（环境变量优先）

**追问怎么接**
- *"为什么错误要转中文？"* → 因为错误信息会**进 AI 的上下文**。`fetch failed` 模型看不懂就瞎编，`数据接口请求超时（10 秒无响应）`它就知道该说什么。
- *"小程序为什么不用 cookie？"* → 真机上 `Set-Cookie` 的自动管理不可靠，所以改由前端显式携带自定义头。**同一套鉴权逻辑，两种凭证来源。**

## 五、面试官必问的 8 个问题

### Q1 这和跟着教程搭的 RAG demo 有什么区别？
三个层次的区别：**一是检索链**（混合召回 + RRF + 交叉编码器重排 + 去重，四级）；**二是异常处理**（每级都有降级、异常有分层语义）；**三是它不是一个 RAG 应用，是三能力合体**（RAG + 工具 + 工作流）。

### Q2 为什么不用 LangChain / LangGraph？
**先手写，再上框架。** 我手写了 45 行的状态图引擎，条件边、状态补丁、循环调度都自己实现过。这样用框架时能看懂它的取舍，而不是当黑盒用。接下来我会用 LangGraph 重写一遍这个图做对照。

### Q3 RAG 效果怎么评估？（⚠️ 你的缺口，按这个答）
**先承认，再给方案**：
> "目前只有定性的判断，没有量化指标——这是我明确知道要补的一块。我的方案是造一组黄金测试题（15 道左右，覆盖事实查询、多跳、政策类、边界），跑**纯向量基线 vs 混合+精排**两版对照，看命中率和 MRR 的差值。基线代码我已经留好了（`knowledge.ts` 里注释保留着纯向量版本），取消注释就能切。"

### Q4 怎么防 AI 乱说话？
三层：**提示词层**（显式否证 + 红线声明）；**契约层**（返回值自解释，明确告诉它"什么都没发生"）；**结构层**（高风险动作必须停在人审节点，不可逆动作永远不交给模型）。

### Q5 工具调用失败怎么办？
先分两类：**数据缺失**（客户不存在、无未结清）→ 异常穿出，最外层拦成 `{found: false}`，**明确终止**；**AI 调用失败**（判断或生成）→ 降级到规则 / 模板，**流程继续**。区别在于前者结果无意义、后者用替代实现仍然有效。

### Q6 为什么催款消息不直接发出去？
因为**发送是不可逆动作**。这类动作不进图、不进工具，工具只产草稿 + `needsApproval` 标签。AI 在对话里也明说了"我没有任何发送消息的能力"——**这条边界必须在提示词里点名写死**，不能靠模型自觉。

### Q7 状态怎么存的？（⚠️ 你的缺口，按这个答）
> "目前**没有持久化**：前端用 `useChat` 把 messages 数组放在 React state 里，每轮整体 POST 给后端，后端是无状态的。同页面不刷新能记住，刷新就丢。
> 图的状态更是只在一次请求内存在——所以我的 `humanApprove → END` 设计，用户第二天回来说'发吧'是接不上的。
> 下一步就是引入 `threadId` + checkpointer，把会话和图状态落到存储，让它支持断点续跑和人审跨时间。"

### Q8 为什么这套东西要给批发商做？
因为我本职就是做批发 SaaS 的（订单豹），我熟悉真实数据长什么样——会员、订单主表 + 明细、SPU + SKU、未收金额在订单上而不是客户上。**这个项目的 mock 数据是按真实 ERP 表结构造的，不是随便编的**：客户表用 `sanbao_member` 的字段、订单带 `order_goods` 嵌套明细、商品走 `goods_sku` + `erp_sku_stock`。
